# ライフゲーム観賞・生態系ビューア Webサイト開発依頼プロンプト（技術選定・実装方針編）

※このプロンプトは、別途共有している仕様書「@docs/requirements-document.md」とセットで利用する想定です。  
ここでは **技術スタックと実装方針** にフォーカスして設計・提案してください。

---

## 0. 前提・ゴール

- **静的ホスティング前提**（バックエンド無し、静的ファイル配信で動作）。
- **ホスティング環境：GitHub Pages**
  - `main` ブランチをソースとして利用するか、`gh-pages` ブランチにビルド成果物を配置する形を想定。
  - デプロイには **GitHub Actions** を用いる（詳細設計は開発者側でベストプラクティスを提案）。
- 使用技術は以下を前提とします：
  - 言語：**TypeScript**
  - フレームワーク：**Svelte**
  - スタイリング：**Tailwind CSS**
  - 描画・アニメーション：**PixiJS**
- 上記を前提に、パフォーマンス・メンテナンス性・拡張性を重視した「現時点でのベストプラクティス」を開発者目線で提案・設計してください。

---

## 1. アーキテクチャ・プロジェクト構成の方針

以下を整理して提案してください：

1. **Svelte アプリ構成**
   - Svelte 単体（+ Vite）での SPA 構成にするか、SvelteKit の静的エクスポート（`adapter-static`）を使うかなど、  
     **GitHub Pages 上での静的ホスティングに最適な構成と理由** を示してください。
   - ルーティング要件は最小限（単一ページ中心）だが、将来的なページ追加を考慮した構成。

2. **ディレクトリ構成案**
   - 例：
     - `src/lib/components/` … 再利用可能な UI コンポーネント
     - `src/lib/features/lifegame/` … ライフゲーム関連ロジック・UI
     - `src/lib/stores/` … Svelte store（状態管理）
     - `src/lib/styles/` … Tailwind カスタム設定や共通スタイル
     - `src/lib/pixi/` … PixiJS 関連のラッパ・初期化コード
   - 実際の構成案と意図（責務分離・メンテ規模など）を説明してください。

3. **型・Lint・フォーマッタ**
   - TypeScript の `strict` 設定の方針。
   - ESLint / Prettier / Stylelint (必要であれば) の導入方針。
   - Svelte 用の ESLint プラグインや推奨設定があれば、それも含めて提案。

## 2. ライフゲームロジックと Svelte / PixiJS の分離設計

### 2-1. ライフゲームコアロジック

- ライフゲームのルール実装は **描画レイヤーから独立した「純粋ロジック」層** として設計してください。
  - 例：`LifeGrid` や `LifeEngine` のようなクラス / 関数群。
  - 型定義（例：`CellState`, `Grid`, `SimulationSettings`, `PresetConfig` など）を明示的に定義。
- 更新アルゴリズムの設計：
  - シンプルな 2D 配列ベースでよいが、パフォーマンスチューニング余地（ビット演算、WebWorker 等）があれば拡張の余地を残してください。

### 2-2. 状態管理（Svelte store）

- グローバルに共有されるべき状態を Svelte の `writable/derived` store で定義してください。
  - 例：
    - `simulationStore`：再生/停止状態、速度、現在ステップなど。
    - `presetStore`：選択中のプリセット、プリセット一覧。
    - `uiStore`：Zen モード、サウンドのオン/オフなど。
- コンポーネントが直接ロジックを持ちすぎないようにしつつ、Svelte のリアクティブさを活かした設計を提案してください。

### 2-3. PixiJS との統合（Svelte コンポーネント設計）

- PixiJS の初期化とライフサイクルを担う専用コンポーネント（例：`<LifeCanvas />`）を定義してください。
  - `onMount` で Pixi アプリケーション初期化。
  - `onDestroy` で Pixi の破棄とリソース解放。
- Svelte の reactivity と Pixi のレンダリングループの境界をどう設計するか提案してください：
  - シミュレーションステップの進行：`requestAnimationFrame` / `Ticker` などの利用方針。
  - Svelte の store 変更時に Pixi の描画をどう更新するか（直接参照するか、イベント経由にするか等）。

## 3. Tailwind CSS によるデザイン・テーマ設計

1. **Tailwind 設定**
   - `tailwind.config.cjs/ts` でどのようなカスタム設定を入れるか提案してください：
     - カラーパレット（Forest, Ocean, Nebula などプリセットと対応する色セット）。
     - フォント設定（見やすく・没入感のあるもの）。
     - アニメーション用の `transition`, `opacity`, `blur` などのユーティリティ。
2. **コンポーネント設計**
   - コントロールパネル、ボタン、スライダーなど UI 要素のスタイル設計方針。
   - 「Zen モード」切り替え時の UI 表示/非表示や透過、フェードなどを Tailwind でどう表現するか。
3. **ダークテーマ / カラーモード**
   - ベースはダーク系 UI を想定し、色覚多様性に配慮したテーマ（モノクロームテーマなど）も Tailwind で切り替え可能にする案を提示。

## 4. PixiJS を用いた描画・アニメーションのベストプラクティス

1. **PixiJS 初期設計**
   - 推奨の PixiJS バージョン。
   - `Application` の作成・リサイズ対応・デバイスピクセル比対応などのベストプラクティス。
   - Canvas サイズとグリッドのマッピング（セルサイズの計算、ズームパラメータの扱い）。

2. **セル描画最適化**
   - 各セルを個別の Sprite とするか、`Graphics` や `Mesh` を使うかなど、パフォーマンス観点での選択と理由。
   - 生死遷移時のフェード・色変化を PixiJS でどう実装するか（alpha/ tint / filter の利用など）。
   - 将来的にエフェクト（ぼかし、グロー、パーティクル）を追加しやすい構造。

3. **アニメーション制御**
   - PixiJS の `Ticker` とライフゲームのステップ更新の同期方法。
   - 「Slow Cinema モード」や速度調整スライダーとの連動設計。

## 5. パフォーマンス・最適化方針

- **パフォーマンス要件：**
  - PC でフルスクリーン表示時にも快適に動くことを目標（60fps 近辺）。
  - スマホではフレームレートやグリッドサイズを自動調整するなどの工夫。

- 具体的な施策案：
  - グリッドサイズに応じた計算負荷の制御（例：大きな画面ではセルサイズを大きめにしてセル数を抑える）。
  - `requestAnimationFrame` ベースの更新と、UI の再レンダーが過剰に走らないような構造。
  - ウィンドウ非アクティブ時に自動で更新間隔を落とす、または一時停止。
  - 必要であれば、後から Web Worker に計算部分を切り出しやすい構造を提案。

## 6. ビルド・デプロイ・GitHub Pages / GitHub Actions

1. **ビルドツール**
   - 使用するビルドツール（例：Vite）と、その設定方針。
   - GitHub Pages の公開パス（`https://<user>.github.io/<repo>/`）に対応するための `base` 設定などがあれば明示。

2. **ビルド成果物**
   - `dist/` などのディレクトリに出力される静的ファイル構成。
   - SPA の場合、リロード時の 404 対応（GitHub Pages 特有の制約への対処）が必要な場合はその方針も提示。

3. **GitHub Actions によるデプロイフロー**
   - 想定フロー例：
     - `main` ブランチに push / pull request マージ → GitHub Actions でビルド → `gh-pages` ブランチへデプロイ、または `main` の `docs/` 配下へ出力。
   - 必要なワークフローファイル（例：`.github/workflows/deploy.yml`）の構成案：
     - 使用する Action（例：`actions/checkout`, `actions/setup-node`, `peaceiris/actions-gh-pages` など）。
     - Node.js バージョン。
     - キャッシュ戦略（`node_modules` など）。
   - 簡単な例で良いので、どのようなステップ構成にするか（checkout → install → build → deploy）を記述。

4. **ローカル開発〜本番反映までのフロー**
   - `npm run dev` でのローカル開発。
   - `npm run build` での本番ビルド確認。
   - `main` へのマージ → 自動デプロイ → GitHub Pages 反映という一連の流れを簡潔に整理。

---

## 7. テスト・品質担保

- 最低限のテスト戦略：
  - ライフゲームロジックに対するユニットテスト（世代更新、境界条件など）。
  - E2E テストが必要であれば、その方針（例：Playwright / Cypress）。
- 型安全性を活かした開発フロー：
  - TypeScript の型エラーを CI（GitHub Actions）で検出。
  - Lint / フォーマットチェックを GitHub Actions に組み込む案があれば提案。
  - 可能であれば pre-commit フック（lint-staged など）の活用提案。

## 8. 開発者として提案してほしいこと

上記の前提を踏まえつつ、以下を開発者目線で **提案 + 簡潔な理由** とセットで提示してください。

1. 最適だと考える **Svelte + TypeScript + Tailwind + PixiJS** の組み合わせ方・構成。
2. プロジェクト初期セットアップ手順（コマンド例 / 主要設定ファイルのポイント）。
3. 将来的に機能追加（プリセット追加・音声機能・ギャラリー機能など）しやすい構造のアイデア。
4. 「眺めて癒やされる」体験を壊さないために、技術的に気をつけるべき点。
5. **GitHub Pages + GitHub Actions** で安定して自動デプロイされるためのベストプラクティス（ブランチ戦略・ワークフロー設計・環境変数の扱いなど）。

このプロンプトをもとに、**実際にすぐ開発に着手できるレベルの設計方針・初期セットアッププラン・デプロイフロー** を提示してください。
